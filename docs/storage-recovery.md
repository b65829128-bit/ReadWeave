# Windows 数据库修复记录

日期：2026-10-15。版本：`0.1.0-alpha.7`。

## 现场复现与证据纠正

用户报告打开任意一本书都提示“原文或引用保存失败，请检查设备存储”。从资源管理器双击交付的 alpha.6，打开《梯度下降的第一步》复现。程序父进程为 Explorer，交付文件哈希与此前记录一致，完整性标记为 Medium。

仅记录固定代码和源码行号的临时诊断确认：删除旧正文块时 SQLite 返回 `SQLITE_CORRUPT (11)`。不是空间不足。实际进程的一致性备份也未通过 `quick_check`；部分表出现跨表页面引用，影响不止正文索引。

此前工具启动环境访问的是 Codex LocalCache 中的完整副本；资源管理器启动访问的数据库已损坏。两者都显示相似的书架，不能用前者的完整性或重开结果证明后者正常。alpha.6 验证记录中的“解决实际打开保存失败”结论已撤回。文件视图差异有证据；数据库最初何时、由哪一次写入损坏没有被确定，不把 SQLite 的历史 WAL 缺陷当作已证实原因。

## 本机数据恢复

- 在实际进程环境通过 [SQLite 在线备份 API](https://sqlite.org/backup.html) 保存完整数据库快照，包含其当前 WAL 视图；损坏原库的完整备份保留在本地 `.local`，未上传、未提交 Git。
- 实际库中的 7 条可读取用户记录，经索引读取和表扫描逐值比较一致。此前已验证完整的 9 条记录副本包含同样的书库及原有笔记、会话。构造恢复副本时以当前 7 条为准，保留当前设置和位置，从完整副本补回笔记、会话两条记录。不是直接回滚到早期书库。
- 当前损坏的快照 / 引用表读出了属于正文块的字段，索引读取失败，不能作为可信引用恢复；其原始字节仍保留在完整损坏库备份。恢复副本沿用完整副本中的正文与 CFI 缓存，原书保持不变。
- 副本完整性、外键和 9 条记录逐值核对通过。在损坏库的独立副本上先演练恢复；另验证源记录指纹改变时拒绝恢复、源文件保持原样。
- 一次性本地修复程序从资源管理器启动，对实际库持有 SQLite 独占锁。重新核对源记录、设备标识、版本以及恢复副本的文件 / 记录指纹，另存完整原库备份后，使用 SQLite Backup 事务恢复，再次核对完整性和记录。没有删除主文件或单独移走 WAL / SHM。

修复操作是针对本次现场和已核对备份执行的一次性恢复。产品没有加入“自动清空损坏数据库”的逻辑。

## 程序改动

已有数据库在迁移、设备登记和用户记录写入前执行 `quick_check`。损坏时停止初始化，保留文件并提示需要备份修复。读取、正文登记、引用服务中的 SQLite 错误分别识别损坏、空间不足、只读权限及占用；不再把这些情况都解释为空间问题，不向界面或日志暴露底层错误中的路径、正文或密钥。

新增原生回归：破坏合成数据库的正文表页面后，启动拒绝继续，主文件字节保持不变、原笔记仍可读取；另覆盖错误分类及底层敏感错误文本不外泄。

## 本轮验证

`npm run check` 通过，53 项单元测试通过；生产浏览器流程 10 / 10；原生测试 29 / 29，通过格式与 clippy 检查。本地样本专用测试按其约定忽略，本轮没有重新宣称两本原文件的原生导入验收。

从资源管理器双击最终 alpha.7，实际打开三本现有书：《梯度下降的第一步》《理解的线索》《资治通鉴》。三本均显示正文，翻页后进度写入成功，无保存失败提示。原先未登记的示例书完成了新的正文登记写入，覆盖了仅命中缓存不能证明可写的缺口。

关闭应用后，由资源管理器启动的只读核验确认：`quick_check=ok`，9 条用户记录、3 本已登记书、66,067 个正文块；与修复副本相比，书籍身份不变，笔记、会话、动作包和设置逐值不变，只有书籍位置和打开时间发生本轮预期更新。另存完整的修复后备份。

随后再次从资源管理器启动最终 alpha.7，打开《资治通鉴》恢复到刚才翻页后的正文位置，无存储错误。第二次在实际环境中只读核验通过：三本书的位置记录指纹与重启前完全一致，所有非书籍记录保持不变，完整性仍为 ok；另存重启验证后的完整备份。

Android、原生文件选择框重新导入和真实模型服务未在本轮验收。没有安装 NSIS、没有发布或推送远程。
