# 本地 EPUB 兼容性与日常使用

日期：2026-10-14。修复版本：`0.1.0-alpha.4`。

## 两本实际样本

经用户反馈指定的本机 EPUB，仅在本机隔离测试中使用。原文件没有修改，正文、原书、截图和提取结果不进入 Git，也没有请求外部模型或其他远程服务。

| 样本                     | 原文件大小 | 阅读章节 | 非空正文段落 | 规范化正文 UTF-16 单位 |
| ------------------------ | ---------: | -------: | -----------: | ---------------------: |
| 《资治通鉴（切块版）》   |  20.59 MiB |      289 |       66,022 |              8,204,363 |
| 《万历十五年（增订本）》 |   8.09 MiB |       32 |        1,938 |                249,368 |

两本 ZIP 的 CRC 均通过；第一本展开约 48.69 MiB，第二本约 8.71 MiB，均在原有压缩包资源限额内。

《资治通鉴》的导入失败来自原型的 50,000 段上限。包内还保留了约 5.43 MiB 的原始整章资源，但这些资源未被阅读 spine 使用；实际阅读章节最大为 86,542 个 UTF-16 单位，没有触发单章限制。不能从包内最大的文件推断本次报错原因。

《万历十五年》的章节使用标准 HTML 命名实体 `&nbsp;`。严格 XML 解析器在不加载出版物外部 DTD 时无法识别该名称，因此过去显示“章节格式损坏”；这个错误不足以说明原书损坏。

## 已实施的修复

- 将前端和 Rust 共用的正文段落限额提高到 100,000 段；前端直接读取同一份 reading contract，正确拒绝第 100,001 段。章节数量和文字总量分别报错。
- 在 XML 解析前，将完整、已知的标准 HTML 命名实体转换为数值字符引用；保留 XML 自带实体及字面转义，预处理跳过 CDATA、注释和处理指令。解码器仅处理名称 token，不解析出版物标记或 DTD；未知名称及已知名称的伪造后缀仍拒绝。
- 自定义 XML 实体声明、未闭合结构、主动内容、危险链接、出版物 CSS / SVG 和自动远程请求继续经过原有拒绝或清理。清理后的 XML、正文提取和 CFI 仍使用相同变换路径；已能导入书籍的 `epub-text-v2` 标识继续沿用。
- 单章超限、章节结构无法解析和段落超限分别显示原因，避免把处理能力限制描述为文件损坏。

这次按实际触发项调整段落处理能力。压缩包 32 MiB、展开 96 MiB、单资源 8 MiB、2048 项、单章源码 2,097,152 个 UTF-16 单位、512 个阅读章节及总文字预算继续有限额。更大的书和复杂版式还需逐步验证，不能据两本样本承诺全面兼容。

## 实际验证

- `npm run check`：48 项单元测试、静态检查和生产构建通过。实体字符、CDATA / 字面转义、危险 URL、未知实体、自定义 DTD 和不闭合结构均有回归覆盖。
- 生产浏览器流程 9 / 9 通过。新增合成书有 51,000 段，实际导入并重开；恶意 EPUB 同时包含命名实体，清理后仍无脚本或远程请求。
- 两本原文件在隔离 Microsoft Edge 中，经与原生相同的内容安全策略，实际完成生产界面导入、显示正文、翻页、返回书架和重开；外部请求为 0。
- Rust 常规测试 22 / 22 通过，另有一项需要本地样本资料的测试默认忽略。100,000 段可登记，超出一段时原有正文与指纹保持完整。
- 对两本书分别显式运行本地样本测试：前端实际提取的段落经过原生原书哈希、段落 / CFI / 字数校验，写入隔离 SQLite，关闭并重建服务后再次核对段落数与指纹，均通过。该证据是原生阅读核心验收；Windows 应用 UI 中导入这两本书和 Android 真机仍需分别记录。
- 首次 Rust 测试因系统 TEMP 目录拒绝创建目录而失败；改用本工作区 `.local/native-test-temp` 后全部通过。没有更改系统目录权限。测试中间提取资料在验证后清理。

当前大书仍需完整提取正文，导入耗时明显超过示例书。按章缓存、避免导入后重复解析和可取消的进度反馈是后续性能工作。

## 密钥处理（alpha.4 当时状态）

“关闭即丢失密钥”是安全存储尚未完成前的临时状态，属于日常使用缺口。长期应提供“在此设备记住密钥”和“清除已保存密钥”，通过原生系统保护保存，继续从书籍数据库、日志和默认备份排除凭据。

Windows 可评估用户范围的 [DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)，其解密通常绑定用户登录身份和计算机；Android 可用 [Android Keystore](https://developer.android.com/privacy-and-security/keystore) 保护加密密钥，再加密保存模型凭据。两者仍需在本项目中验证保存、重启读取、删除、错误恢复和服务地址隔离，官方 API 的存在不等于本项目已完成验收。

以上内容记录 alpha.4 时的待办。跨平台实现与真机验收进展见下文。

## alpha.8 密钥安全存储

原生 Windows 客户端使用 Windows 凭据管理器；Android 使用 Android Keystore 保护的应用凭据存储。启动时只读取“密钥是否存在”的状态；提交模型请求时由 Rust 原生端直接读取密钥，前端 IPC 请求不再携带密钥。设置页可保存、替换或删除密钥；空白输入会保留现有密钥。系统凭据不进入 SQLite、日志、JSON 备份或恢复输入。Android 备份与设备迁移规则会排除加密凭据文件。

浏览器预览仍把密钥限制在当前运行的内存中，不提供持久化。Windows 凭据管理器已通过合成凭据写入、读取和删除测试；Android 16 / API 36 真机已通过 APK 启动以及合成值保存、强制重启保留和删除后的重启检查。没有使用真实密钥或发送模型请求。连续触摸阅读及其他完整平台验收仍待完成，详见 [验证记录](validation.md)。
